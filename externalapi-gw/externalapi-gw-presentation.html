The problem · Why this matters

A gateway endpoint is exacting, spec-driven plumbing.

The Gateway is the public API surface. Every GET endpoint has to line up precisely with the ADO ticket — done by hand it's careful, repetitive translation work:

  • Controller + query wired to the downstream service client
  • Request/response DTOs that match the ticket's ViewModel property-for-property
  • Reference objects and enum/lookup shapes per the endpoint spec
  • Integration tests, each mapped to its ADO TestCaseId for traceability
  • Rebuild so the NSwag / APIM template regenerates, then drive the build green

The tax: none of it is the interesting part — it's faithful transcription of a spec into a fixed file set. A single missed DTO property or unmapped test case means rework downstream.

It's exactly the work that rewards a machine that never gets bored.

Trust · Why the caveat is a feature

It stays honest, and it never pushes.

  • DTOs are verified, not guessed — #256324's request/response DTOs were diffed against the ticket ViewModel: 36 properties, exact match.
  • Test traceability built in — #269979 mapped all 18 ADO TestCaseIds to integration tests automatically.
  • Honest build status — when the scheduled shell couldn't reach the private NuGet feed, it labelled the run build-unverified rather than claiming green.
  • Read-only, stops at READY — no commit, no push, no PR, no ADO change. The final build + push is always a human decision.

The *unverified build was a sandbox limit, not a code fault.

The task shell isn't authenticated to the private RWInternalFeed, so dotnet restore can't run there. The file set was complete and correct; the developer compiles interactively before pushing — which they were always going to do anyway.

A tool that says "I couldn't verify this" is safer than one that pretends it did.
