The problem · Why this matters

Review is where good work waits in line.

A microservices PR touches architecture, security, data/tenancy, contracts, and tests at once. Reviewing it well is slow — and it competes with the reviewer's own deadlines:

  • PRs sit for hours or days until a reviewer has a free block
  • A careful pass against the architecture standard takes real focused time
  • Under pressure it's easy to skim — and miss a security or tenancy issue
  • Depth and consistency vary by who reviewed it and how busy they were

The cost isn't just time — it's variance. The same PR gets a thorough review or a rubber stamp depending on the week.

A consistent, always-on first pass changes that.

The method · Not a linter

Five expert reviewers, then a verifier that tries to prove them wrong.

Each reviewer reads the whole changed files against its slice of the standard — not a regex over the diff. Findings are then challenged before they're reported, so what reaches you is real.

The catch · Why the finding is trustworthy

It found a real auth gap — and proved it before reporting.

  • R2 flagged new paged actions on CalendarConfig with no [Authorize] — a potential open endpoint.
  • The obvious false-positive: maybe the base class AbstractMicroserviceController supplies [Authorize] for everyone.
  • Verifier checked the base class and sibling controllers directly — the base does not carry it; siblings declare it explicitly.
  • Verdict: UPHELD. Real finding, escalated to reject — not a guess.

This is the difference between a linter and a reviewer.

The adversarial step exists to kill plausible-but-wrong findings. Here it did the opposite — it confirmed a security issue that a fast human pass could easily wave through, because "the base class probably handles auth" is exactly the assumption people make.

You arrive to a verified finding with the file, the line, and a suggested fix.
