MS PR-Review — Orchestration Flow STAGE 4

One headless Claude process acts as an orchestrator over the sis-services microservices monorepo: it gathers each PR read-only, fans out five reviewers in parallel, adversarially verifies every error, then merges and renders. Runs unattended 6×/day (Mon–Fri). The in-repo microservices-architecture.md is the authoritative standard.

▼   for each PR, one at a time   ▼

2 Gather the change serial · read-only git/gh

The orchestrator is the only actor that touches git/gh. It fetches refs/pr-review/<n>, reads each whole changed .cs file at head (+ base), notes the owning Services.{Domain}/, caches the text, then deletes the temp ref immediately. Sub-agents get this text inline — they fetch nothing.

Each is a no-tool sub-agent given the PR metadata, its files’ full text, its rubric sections + the authoritative arch-doc rules, and the finding shape. Each returns a JSON array of findings.

3 Merge & dedupe serial

Concatenate the five arrays; dedupe on (file, line, category) keeping highest severity + richest record; normalize to the 20 MS categories so the report groups cleanly.

4 Adversarially verify every error NEWparallel

Each error finding goes to a verify sub-agent that tries to disprove it against the quoted rule (arch-doc first) + file slice → UPHELD / REJECTED / WRONG_SEVERITY. Uphold on uncertainty. Kills MS false positives (e.g. a PagedResult<T> query or internal handler wrongly flagged).

5 Finalize, score & render serial

Drop rejected, downgrade wrong-severity, then recompute E/W/I (single source of truth). Apply the verdict ladder, inject the data JSON into pr-review-ms-template.html, and write PR-<n>-<slug>.html. Emits PR #<n> REVIEWED: ….

✓ Read-only guarantee & summary wrapper

Asserts branch + HEAD are byte-for-byte unchanged, cleans any stray refs/pr-review/*, releases the lock, and logs PR REVIEW RUN COMPLETE. You open the HTML reports in Downloads\PR Review MS\ and act on GitHub manually — nothing is posted automatically.

What changed vs Stage 3
Stage 3 — one Claude pass reads all files and applies all 15 rubric sections monolithically, sequentially.
Stage 4 — orchestrator delegates to 5 parallel reviewers, then verifies errors adversarially, then integrates.
False positives — the MS return-type split (query PagedResult<T> vs command ActionResult<T>) and internal handlers/fixtures are disproved before an error ships.
Contention — orchestrator owns all git/gh serially; sub-agents use no tools, so the shared monorepo is never touched in parallel.
Still strictly read-only · idempotent (1 PR = 1 HTML) · unattended within the 1-hour task limit · same design as the gateway (GW) reviewer.
