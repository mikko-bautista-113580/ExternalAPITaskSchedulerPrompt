GW PR-Review Automation

From Stage 3 to Stage 4

How I upgraded my automated pull-request reviewer from a single linear pipeline into a parallel, self-verifying orchestrator — same job, faster and more accurate.

A quick, step-by-step walkthrough

The job (unchanged)

What the reviewer does

Every weekday, six times a day, it automatically finds open PRs, reviews the code against our standards, and writes a report — read-only, nothing posted to GitHub without me.

🎯 Same goal in both stages

  • Find eligible open PRs
  • Review changed files vs the rulebook
  • Produce one HTML report per PR

🔄 What we're changing

  • Stage 3 — one long sequential pass
  • Stage 4 — parallel reviewers + a verify step
  • Only how the review runs changes

STAGE 3 In plain steps

2

Simple and reliable — but slow, and whatever a skill flags goes straight into the report, even if it's a false alarm.

The problem to solve

Why move to Stage 4?

🐢 Sequential = slow

  • Six reviews run back-to-back
  • Total time = the sum of every step

⚠️ No second opinion

  • A wrong “error” ships as-is
  • I waste time double-checking false alarms

Goal: run the reviews at the same time, and fact-check every error before it reaches the report.

STAGE 4 In plain steps

1
Find & filter PRsExactly the same as before.
2
Orchestrator gathers the changeOne controller reads all the code once (read-only) and hands it to the reviewers.
3
5 reviewers run at the same time NEWEach owns a slice of the rulebook (architecture, security, data, quality, testing) and returns its findings.
4
Merge the findingsCombine all five, remove duplicates.
5
Fact-check every error NEWA separate agent tries to disprove each error. False alarms are dropped before the report.
6
Decide & reportRecount → approval decision → generate HTML → save. Same output as Stage 3.
